# Licensing options

Research for [issue #8 "Licensing options"](https://github.com/vicvancooten/mail/issues/8) (child of #1, "Wayfinder map: Mail PoC — technology, architecture & scope").

Question: which license fits best for the project — AGPL (protective copyleft), MIT/Apache-2.0 (permissive/frictionless), or BSL/fair-source (delayed open, commercial optionality) — given the project (Sync Backend + web Client, one monorepo) is being developed closed-source now, with likely open-sourcing later?

This document does not recommend a license — it lays out what each candidate actually requires/permits, sourced to primary texts and official vendor statements, so the choice can be made deliberately.

---

## 1. AGPL-3.0 (protective copyleft)

### What it actually requires

AGPL-3.0 is GPL-3.0 plus one added clause. [GPL-3.0's own text](https://www.gnu.org/licenses/gpl-3.0.en.html) defines "convey" (section 0) as any propagation that enables other parties to make or receive copies, and explicitly excludes mere network interaction: *"Mere interaction with a user through a computer network, with no transfer of a copy, is not conveying."* Under plain GPL-3.0, running a modified program as a network service — never handing anyone a copy of the binary — does not trigger the source-disclosure obligation at all. This is the well-known "ASP/SaaS loophole" that AGPL was written to close, as described on the FSF's dedicated page [Why the GNU Affero GPL](https://www.gnu.org/licenses/why-affero-gpl.html): *"When D modifies the program, he might very likely run it on his own server and never release copies. Then you would never get a copy of the source code of his version."* That page also flags AGPL's limit: it does not address "Service as a Software Substitute" (SaaSS) concerns about user control over their own computing — it only guarantees *source* access, not deployment control.

The operative text is [AGPL-3.0 section 13, "Remote Network Interaction"](https://www.gnu.org/licenses/agpl-3.0.en.html), quoted in full:

> "Notwithstanding any other provision of this License, if you modify the Program, your modified version must prominently offer all users interacting with it remotely through a computer network (if your version supports such interaction) an opportunity to receive the Corresponding Source of your version by providing access to the Corresponding Source from a network server at no charge, through some standard or customary means of facilitating copying of software."

Section 13 also permits combining AGPL-covered code with plain GPLv3 code in one work, each part staying under its own license.

### How the trigger interacts with a backend + client split

The clause triggers on **modifying and letting users interact with the modified version over a network** — it is about who is served, not which artifact (backend vs. client) is modified:

- **Sync Backend**: this is exactly section 13's target case. If the backend is AGPL-covered and someone runs a modified version reachable by any user over a network, that operator owes those users the modified source. A private individual running an unmodified or self-modified copy for their own single-user access is not "conveying" to a third party in the GPL sense, and even where it counts as network interaction, the obligation is to offer source *to the users interacting with it* — so a strictly personal deployment (one household, the deployer is the only interacting user) has no outside party to owe source to, since there's no *other* user receiving the modified service.
- **Client**: the same clause applies if the client code is itself modified and served to other users over a network (e.g., a hosted PWA build) — the clause is not backend-specific, it applies to any AGPL-covered program a modifying party makes network-available to others.
- **Household-scale vs. multi-tenant SaaS**: the FSF's texts don't carve out an explicit "private/household use" exception by name, but the mechanism does the same work — the obligation runs to "all users interacting with it remotely," so a single deployer running the software only for themselves (or their own household, where the deployer controls the instance and no separate third party is "a user" being served a modified version by someone else) does not create a party the clause obligates you to serve source to. The clause becomes operationally significant once a **third party who is not the modifying party** starts interacting with the modified service — i.e., precisely the moment a household deployment tips into a hosted offering for other people. This reading follows directly from the "users interacting with it remotely" language in section 13 and the FSF's own framing of the loophole as being about *other people* running your code as a service without giving *those people* the source — it is not drawn from a specific FSF FAQ entry naming "private use," since that exact page could not be fetched during this research (see note below).

**Source-access note**: the [FSF's GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html) was requested per the task brief specifically for its "conveying" and network-interaction commentary, but the live page returned HTTP 429 (rate-limited) on every fetch attempt during this research session and could not be quoted directly. The "convey"/"propagate" definitions and private-use conclusions above are instead drawn directly from the GPL-3.0 license text itself (section 0, quoted via search excerpt from [gnu.org/licenses/gpl-3.0.en.html](https://www.gnu.org/licenses/gpl-3.0.en.html)) and from [why-affero-gpl.html](https://www.gnu.org/licenses/why-affero-gpl.html), both primary FSF pages. Re-attempting `gpl-faq.html` directly is recommended before this decision is finalized, to confirm there is no more specific private-use carve-out language.

### Implications for a future hosted/commercial offering

AGPL does not block the project itself from also selling a commercial or hosted version — it constrains *other people's* redistribution and hosting, not the copyright holder's own options. The FSF's own page [Selling Exceptions to the GNU GPL](https://www.gnu.org/philosophy/selling-exceptions.html) documents this directly: a copyright holder can release code under GPL/AGPL publicly and **separately** sell a proprietary-use exception to paying customers, because "selling exceptions depends fundamentally on using a copyleft license... only the copyright holder can grant" permission to embed the code outside the copyleft terms — someone who merely received the code under GPL cannot resell that permission. The FSF cites Qt/Trolltech as the historical example of this pattern. This is the mechanism behind the common "open core" / dual-license business model: AGPL's copyleft is strict enough that competitors (especially SaaS competitors) are commercially deterred from building on the code without either open-sourcing their own service or buying a commercial license — which is explicitly why HashiCorp, Elastic, and MongoDB each cited "cloud providers monetizing without contributing back" as their reason for moving to *more* restrictive terms (BSL/SSPL) rather than staying permissive (see §2 below and the BSL/fair-source section). AGPL is, in that sense, leverage for a dual-license business model rather than an obstacle to one — provided the project keeps full/sole copyright (see §3 on CLAs).

### Contributor agreements

See §3 (cross-cutting) below; MongoDB's case is the primary worked example of a CLA enabling a later AGPL-adjacent relicense.

## 2. MIT / Apache-2.0 (permissive, frictionless)

### What they actually require

**MIT** — full text via [SPDX's canonical copy](https://spdx.org/licenses/MIT.html): grants permission "to use, copy, modify, merge, publish, distribute, sublicense, and/or sell copies of the Software," with exactly one condition — "The above copyright notice and this permission notice... shall be included in all copies or substantial portions of the Software." No copyleft, no patent grant (MIT addresses copyright only, not patent rights), no attribution-in-UI requirement beyond preserving the notice in copies of the software itself. [OSI's license list](https://opensource.org/licenses) confirms MIT is OSI-approved (SPDX id `MIT`, listed under "Popular / Strong Community").

**Apache-2.0** — full text at [apache.org/licenses/LICENSE-2.0](https://www.apache.org/licenses/LICENSE-2.0): grants a perpetual, worldwide, royalty-free copyright license to reproduce/prepare derivative works/distribute, **plus an express patent license** ("a perpetual, worldwide, non-exclusive, no-charge, royalty-free, irrevocable... patent license to make, have made, use, offer to sell, sell, import, and otherwise transfer the Work") — this is the key differentiator from MIT. It carries a **patent-retaliation clause**: "If You institute patent litigation against any entity alleging that the Work... constitutes direct or contributory patent infringement, then any patent licenses granted to You under this License... shall terminate." Redistribution requires: including a copy of the license, marking modified files with a notice of change, retaining existing copyright/patent/trademark/attribution notices, and reproducing a `NOTICE` file's attribution content if present. No copyleft/share-alike obligation — Apache-2.0 "permits adding alternative terms and creating proprietary Derivative Works, provided the original work's conditions remain satisfied." [OSI confirms Apache-2.0 is OSI-approved](https://opensource.org/licenses) (SPDX id `Apache-2.0`).

For a self-hosted client-server app, neither license imposes *any* network-use or source-disclosure trigger — there is no equivalent to AGPL section 13 in either. A vendor could take a permissively-licensed Sync Backend, host it as a competing SaaS with proprietary modifications, and owe the community nothing beyond the copyright/attribution notice.

### Implications for a future hosted/commercial offering

Permissive licensing does not prevent the project from also selling a hosted or enterprise version — it just does not use the license itself as competitive leverage. Anyone (including this project) can build a proprietary offering on MIT/Apache-2.0 code without needing an exception or CLA-based relicense, because the license already grants that freedom to everyone, including third-party competitors. This is the frictionless end of the spectrum: fastest community adoption and easiest downstream reuse, but no license-based protection against a well-resourced third party (e.g., a cloud vendor) operating a competing hosted service off the same code with no reciprocity obligation.

## 3. BSL 1.1 / Fair-Source (FSL) — delayed open, commercial optionality

### What BSL 1.1 actually permits/restricts

Primary text: [mariadb.com/bsl11](https://mariadb.com/bsl11/) (MariaDB Corporation, co-drafted with Heather Meeker and OSI co-founder Bruce Perens, released 2017). Key mechanics, quoted/paraphrased from the license itself:

- **Grant**: the licensor permits you to "copy, modify, create derivative works, redistribute, and make non-production use" of the Licensed Work by default. Production use requires either an **Additional Use Grant** the licensor specifies (e.g., "you may use this in production up to N nodes"), a separately purchased commercial license, or not using it in production at all.
- **Change Date / Change License**: automatically converts on the earlier of a Change Date the licensor specifies, or **the fourth anniversary of first public distribution** — whichever comes first. On that date, "the Licensor hereby grants you rights under the terms of the Change License, and the rights granted in the paragraph above terminate." MariaDB's covenants require the Change License to be GPL 2.0-or-later or a compatible license, so the work is guaranteed to land on a real OSI-approved copyleft license eventually.
- **Explicit non-open-source disclaimer**: the license text itself states "The Business Source License (this document, or the 'License') is not an Open Source license" — it is source-available, not open source, during the restricted period.
- Violating the use restriction "automatically terminate[s] your rights under this License for the current and all other versions."

### What FSL (Sentry's evolution of BSL) actually permits/restricts

Primary source: [fsl.software](https://fsl.software/), maintained by Sentry. Framed as "you can do anything with FSL software except undermine its producer" — broad rights to run, study, modify, and redistribute, with the one restriction being **use as, or to build, a competing commercial product/service** (Sentry's own framing calls this preventing "harmful free-riding"). Every FSL-licensed release **automatically converts to Apache-2.0 or MIT (licensor's choice) exactly two years after that version's release** — a materially shorter and more predictable window than BSL's up-to-4-year term, and the license text ships in two ready variants, `FSL-1.1-MIT` and `FSL-1.1-ALv2` (per [SPDX](https://spdx.org/licenses/FSL-1.1-MIT.html)). Sentry frames FSL as one instance of a broader "**Fair Source**" category it created, defined (per Sentry's [Sentry is now Fair Source](https://blog.sentry.io/sentry-is-now-fair-source) post, found via search) as software that is (1) publicly readable, (2) usable/modifiable/redistributable with minimal restrictions to protect the producer's business model, and (3) subject to "delayed Open Source publication" (DOSP).

### Why companies have adopted BSL/FSL/SSPL — official rationale (primary sources)

- **MariaDB / MaxScale**: created BSL specifically so a company could publish source openly while reserving commercial production use, guaranteeing eventual open-sourcing via the Change Date mechanic ([mariadb.com/bsl11](https://mariadb.com/bsl11/)).
- **Sentry** relicensed from open source to BSL in 2019, per its own blog ([Re-Licensing Sentry](https://blog.sentry.io/relicensing-sentry/)) — stated goals were letting anyone run Sentry for themselves or their business, no functional gap between the cloud product and the open code, and minimal usage limitations, with the real target being protection from other companies reselling their work. In 2023 Sentry moved from BSL to FSL, explained in [Introducing the Functional Source License: Freedom without Free-riding](https://blog.sentry.io/introducing-the-functional-source-license-freedom-without-free-riding/): Sentry felt BSL's per-project "Additional Use Grant" produced inconsistent terms across projects, and FSL standardizes the restriction and shortens the open-sourcing window to 2 years.
- **HashiCorp** moved all core products (Terraform, Vault, Consul, etc.) from MPL-2.0 to BSL 1.1 in 2023, per its own post [HashiCorp Adopts Business Source License](https://www.hashicorp.com/en/blog/hashicorp-adopts-business-source-license): stated rationale was that "other vendors... take advantage of pure OSS models, and the community work on OSS projects, for their own commercial goals, without providing material contributions back," and that vendors offering competing services "will no longer be able to incorporate future releases, bug fixes, or security patches." HashiCorp's APIs/SDKs/libraries stayed MPL-2.0; only the core product license changed. **Community response**: the [OpenTofu announcement](https://opentofu.org/blog/opentofu-announces-fork-of-terraform/), which became a [Linux Foundation project](https://www.linuxfoundation.org/press/announcing-opentofu), forked the last MPL-2.0 Terraform commit specifically because HashiCorp did not reverse the BSL change, seeking "a well-known and widely-accepted license that companies can trust, that won't suddenly change in the future" — OpenTofu itself ships under MPL-2.0. This is the concrete risk case for BSL-style moves: an existing open community can fork rather than accept a licensing change after the fact, though note this scenario presupposes there already was an external contributor community, which does not yet apply to this project (see §4).
- **Elastic** moved Elasticsearch/Kibana from Apache-2.0 to a dual SSPL/Elastic-License model in 2021, announced (with since-criticized framing) as ["Doubling down on open"](https://www.elastic.co/blog/licensing-change) — Elastic's stated reason: "some cloud service providers have taken open source products and provided them as a service without investing back into the community," diverting funds from reinvestment. AWS responded by forking the last Apache-2.0 code as OpenSearch. In 2024 Elastic reversed course, announced in [Elasticsearch Is Open Source. Again!](https://www.elastic.co/blog/elasticsearch-is-open-source-again): Elastic added **AGPL-3.0** as a third licensing option alongside SSPL and ELv2 (not a replacement — existing SSPL/ELv2 users are unaffected), explicitly because AGPL is OSI-approved and, per founder Shay Banon, "paves a path, with OSI, towards more Open Source in the world," citing Grafana's AGPL adoption as a precedent that didn't hurt usage. This is a direct primary-source data point that a company burned by the "not really open source" perception of SSPL chose **AGPL**, not a permissive license, to credibly re-enter "open source" while retaining copyleft-style protection.
- **MongoDB** moved from AGPL-3.0 to its own **Server Side Public License (SSPL)** in 2018, described on MongoDB's own licensing page ([mongodb.com/legal/licensing/server-side-public-license](https://www.mongodb.com/legal/licensing/server-side-public-license)). SSPL's operative section 13 goes further than AGPL: "If you make the functionality of the Program or a modified version available to third parties as a service, you must make the **Service Source Code** available... at no charge" — and "Service Source Code" is defined to include not just the program but *all* supporting infrastructure ("management software, user interfaces, application program interfaces, automation software, monitoring software, backup software, storage software and hosting software") needed for someone to run an equivalent service. This is intentionally broader than AGPL precisely to close what MongoDB saw as a remaining AGPL "ASP loophole" for large-scale hosted competitors.

### OSI's position: BSL, FSL/"fair source", and SSPL are NOT OSI-approved open source

This is an explicit, load-bearing primary-source finding. [OSI's official blog post, "The SSPL is Not an Open Source License"](https://opensource.org/blog/the-sspl-is-not-an-open-source-license), states OSI rejected SSPL because it violates the Open Source Definition on two counts: discrimination against a field of endeavor (cloud hosting, OSD #6) and imposing obligations on unrelated software in the user's stack (OSD #9); OSI's board called such source-available-but-restricted licenses "fauxpen" source when marketed as open source — "claiming software has all the benefits and promises of open source when it does not." The same OSD #6 reasoning is why **BSL was never submitted for/granted OSI approval** and its own text says so outright ("this document... is not an Open Source license," per [mariadb.com/bsl11](https://mariadb.com/bsl11/)). Sentry's FSL/"Fair Source" framing is explicit about the same point — it is "NOT an Open Source license (OSI definition) during its initial term" (per [fsl.software](https://fsl.software/) and related SPDX entries). The practical implication for this project: if "open source" (in the OSI/community-recognized sense) is a goal for the eventual public release, BSL/FSL only reaches that state **after the change date/period elapses** — during the restricted window, calling the project "open source" would draw the same criticism Elastic received in 2021.

### Implications for a future hosted/commercial offering

BSL/FSL are purpose-built for exactly this project's stated sequencing (closed now, open later): they let the project publish source immediately (readable, forkable-with-restrictions, contributable) while contractually reserving the commercial/hosted right to itself until a chosen date, at which point the code becomes genuinely open (Apache-2.0/MIT/GPL, licensor's choice at adoption time). Unlike AGPL, which relies on general copyleft mechanics to deter competitors, BSL/FSL state the deterrent directly as a use restriction, which is more legally precise about what's disallowed but is also the trait OSI/FSF-aligned communities react to as "fauxpen" if described as "open source" prematurely.

## Cross-cutting: contributor agreement (CLA/DCO) implications

**Does license choice require a CLA to preserve future relicensing?** Only if the project wants to *change* the license (e.g., relicense to something stricter/different, or dual-license against outside contributors' wishes) after those contributors' code has landed. A permissive inbound license without any CLA already grants the project (and everyone else) broad reuse rights, so relicensing risk is lower there; a copyleft or source-available project that wants the *option* to sell exceptions or later relicense needs either sole copyright (no external contributions) or a CLA that assigns/broadly licenses contributor rights back to the project.

- **AGPL/dual-license precedent — MongoDB**: MongoDB required (and still requires) contributors to sign the MongoDB/10gen Contributor Agreement — described as "a modified version of the Apache Software Foundation's CLA" — before any external code is accepted, submitted via a Google form matching the contributor's GitHub username (per community-forum and repository documentation referencing [mongodb.com](https://www.mongodb.com)). MongoDB's 2018 move from AGPL-3.0 to its own SSPL ([mongodb.com/legal/licensing/server-side-public-license](https://www.mongodb.com/legal/licensing/server-side-public-license)) was only possible license-wide because that CLA gave MongoDB the rights needed to relicense contributed code — without it, MongoDB would have needed unanimous consent from every external contributor whose code remained under the old license. This is the canonical example of a CLA existing specifically to preserve future relicensing optionality on a copyleft base.
- **BSL/fair-source precedent — HashiCorp**: HashiCorp requires every contributor to any `hashicorp` GitHub-org project to sign its CLA (text at [hashicorp.com/en/cla](https://www.hashicorp.com/en/cla)), stated rationale being that it "removes any ambiguities or uncertainties caused by not having a CLA and allows users and customers to confidently adopt our projects," and it grants HashiCorp a perpetual, irrevocable copyright *and* patent license over contributions usable in commercial products. This is the standard pattern for any project (BSL, FSL, or otherwise) that wants to retain the unilateral right to change license terms or sell commercial/hosted variants including community-contributed code.
- **Permissive-license precedent**: broadly permissive projects typically need no CLA at all, or use a lightweight DCO instead, because the permissive inbound license already grants everyone (including the maintainers) the reuse rights a CLA would otherwise secure. The canonical DCO text, used by the Linux kernel and widely adopted elsewhere, is at [developercertificate.org](https://developercertificate.org/): contributors certify per-commit (via `git commit -s`) that they either authored the contribution and have the right to submit it under the project's license, or are passing through prior work they have the right to submit, without transferring copyright or signing a separate legal document. It functions as "a lighter-weight alternative to Contributor License Agreements."

**For this project specifically**: whichever family is chosen, a CLA (or lack of one) only starts mattering once there are external contributors — which the project does not have yet (see §4).

## 4. Timing / sequencing concerns for this project

### Can the license choice be deferred?

Largely yes, with caveats. Concretely for this repo:

- **No CLA question exists yet.** A search of this repository found no `package.json`, no lockfile, and no code — `git log --all --diff-filter=A --name-only -- "**/package.json"` returns nothing, and `find` for `package.json`/`*.lock` outside `node_modules` returns nothing. The repository currently contains only two ADRs ([0001-companion-sync-backend.md](../adr/0001-companion-sync-backend.md), [0002-react-vite-spa-client.md](../adr/0002-react-vite-spa-client.md)), `CONTEXT.md`, `README.md`, and agent/skill tooling. There is no external-contributor question to resolve today, so a CLA/DCO decision can safely wait until (if) outside contributions are solicited — consistent with the general pattern above that CLA/DCO only matters once contributors exist.
- **The license *label* on first public code is not free to defer indefinitely once code ships publicly**, because changing a published license later requires either sole copyright (true today, since there's no code yet and presumably no external contributors) or a CLA obtained in advance. Practically: the project can stay unlicensed/proprietary internally for as long as it wants (no OSS obligations attach to unpublished, undistributed code under any of these licenses — see the GPL "convey" analysis in §1), but the moment source is shared with any outside party (even a beta tester, even under a private repo invite in some readings, though "conveying" specifically concerns distribution/copies not mere access) the chosen terms start to bind. Since AGPL, BSL/FSL, and permissive licenses all differ in what they allow that outside party to *do* with the code once shared, picking the license before the first external disclosure — not necessarily before writing any code — is the real constraint.
- **BSL/FSL's Change Date is easiest to set later rather than earlier**: because BSL/FSL's core value is "delayed open" from a clock that starts at first public distribution, closed development now doesn't burn any of that clock — the Change Date only starts counting once the code is actually published under BSL/FSL, so there is no cost to deferring the decision to adopt BSL/FSL specifically until first public release.
- **AGPL/permissive have no such clock**, so deferring is equally free for them; the main practical driver for deciding *earlier* rather than later is dependency selection (below), since dependencies chosen during the closed-source phase can already constrain the eventual license before the "license decision day" arrives.

### Dependency-license risk — actual check of this repo

Per the task instructions, the repo was searched directly: `find /home/vic/dev/personal/mail -name package.json -not -path "*/node_modules/*"` returns **no results**, there are no lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`) anywhere in the repo, and `git log` shows no commit ever added a `package.json`. **The project has not started writing code yet** — it is presently ADRs and domain documentation only (confirmed via the repo's own `docs/adr/` and `CONTEXT.md`). Consequently:

- **There are currently zero runtime or dev dependencies to audit, and therefore no GPL/AGPL/copyleft dependency conflicts exist today.** This is a genuinely clean slate, not a "we didn't check" gap.
- **This makes dependency-license risk purely forward-looking and fully avoidable**: the two ADRs on file already commit to a stack — Vite + React + TanStack Router/Query for the Client ([ADR 0002](../adr/0002-react-vite-spa-client.md)), and a self-hosted Sync Backend speaking IMAP/SMTP ([ADR 0001](../adr/0001-companion-sync-backend.md)) — and React, Vite, and TanStack Router/Query are, as of their current public releases, MIT-licensed per their respective npm/GitHub license metadata (not independently re-verified line-by-line in this pass since no `package.json` exists yet to pin exact versions; recommended to confirm at the point dependencies are actually pinned). The main dependency-selection risk to actively manage is **IMAP/SMTP libraries**, since that ecosystem includes some GPL-licensed clients (e.g., historically-GPL mail/parsing libraries exist in several language ecosystems) — whichever IMAP/SMTP library is chosen for the Sync Backend should be checked individually for its license before being pinned, because a GPL (not just AGPL) *library* linked into the backend can already force the whole backend to GPL terms on distribution regardless of what license the project later chooses for its own code, and an AGPL library would extend that obligation to network use as well.
- **General rule this project should apply going forward**: a copyleft (GPL/AGPL) *dependency* is more constraining than a copyleft *choice for the project's own code* — depending on a GPL library forces the combined work to GPL terms even if the project wants to be Apache-2.0/MIT/BSL, because copyleft propagates through linking/derivative-work status regardless of the including project's preference. This means dependency license hygiene should start now, during the closed-source phase, even though the project's *own* license choice can be deferred — closed-source development does not exempt code from a dependency's copyleft terms once that code is ever distributed or (for AGPL dependencies) served over a network, only from the project's *own* licensing decision.

## Comparison framing (for the decision-maker)

Each family optimizes for a different strategic intent; none is strictly dominant.

| | **AGPL-3.0** | **MIT / Apache-2.0** | **BSL 1.1 / FSL** |
|---|---|---|---|
| Strategic intent | Protective copyleft — keep improvements public, deter free-riding hosted competitors, while explicitly preserving the copyright holder's own right to sell exceptions ([selling-exceptions.html](https://www.gnu.org/philosophy/selling-exceptions.html)) | Frictionless adoption — maximize reuse, community trust, and integration into other projects; no leverage against a competitor hosting the same code | Commercial optionality with a credibility cost now, credibility gain later — reserve commercial/hosted rights on a timer, publish source immediately, convert to a real OSI license automatically |
| OSI-approved / uncontested "open source" label | Yes ([gnu.org text](https://www.gnu.org/licenses/agpl-3.0.en.html); Elastic re-added it in 2024 specifically to regain this label — [elastic.co/blog](https://www.elastic.co/blog/elasticsearch-is-open-source-again)) | Yes, unambiguously ([opensource.org/licenses](https://opensource.org/licenses)) | No, during the restricted period, by the license's own text and by [OSI's explicit position](https://opensource.org/blog/the-sspl-is-not-an-open-source-license) — becomes a real OSI license only after the Change Date |
| Blocks the project's own commercial/hosted offering? | No — reserves that right to the copyright holder via dual-licensing/exceptions, at the cost of requiring sole copyright or a CLA if there are outside contributors | No, but grants the *same* freedom to competitors, so it offers no license-based protection | No — this is the license family explicitly designed around this need, at the cost of not being "open source" until conversion |
| Risk if adopted after a community exists | Existing permissively-licensed contributors can't be forced onto AGPL without a CLA/consent | Low — permissive-to-permissive or permissive-to-copyleft changes rarely provoke forks since users already had full rights | High, if there already is an open-source community: see [HashiCorp → OpenTofu](https://opentofu.org/blog/opentofu-announces-fork-of-terraform/) and [Elastic → OpenSearch](https://www.elastic.co/blog/licensing-change) — both forked rather than accept the change. **Not currently a risk for this project**, which has no external community yet (§4) |
| Fit for "self-hosted household app" framing specifically | Section 13's trigger is about serving *other* users a modified version over a network — a strictly single-operator/household deployment likely never crosses that line, so AGPL's practical bite is aimed at future multi-tenant hosting, not personal self-hosting | No network trigger exists either way — self-hosting a permissively-licensed backend carries no different obligation than any other use | The "non-production use" default and "no competing service" restriction target commercial competitors, not personal self-hosters — BSL/FSL both anticipate individuals running the software for themselves as an explicitly intended use case (HashiCorp, Sentry, and MariaDB all frame this as unaffected) |

The open questions for the human decision-maker: how much weight to put on being credibly "open source" from day one of any public release versus reserving a commercial runway; whether a future CLA is worth the friction it may add if/when outside contributors appear; and whether the deterrent value of AGPL's copyleft (proven by MongoDB, Elastic, and HashiCorp all citing "SaaS competitors free-riding" as their reason to move to *stricter*, not looser, terms) is preferred over BSL/FSL's more explicit and legally direct non-compete restriction, given that the former carries the OSI/FSF "real open source" label immediately and the latter only after its change date.
