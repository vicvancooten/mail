# Deployment is a single-image, two-service compose stack

A Mail instance is a root `compose.yaml` with exactly two services — `app` (one Node container running Fastify, every Mail Account's sync loop, and the Client bundle it was built with) and `postgres` — plus one named volume, configured entirely by environment variables, pulling versioned images from GHCR and running its own migrations at boot. The operator brings their own reverse proxy and TLS. This keeps the whole deployment surface to two nameable things (`pgdata` and `.env`) at single-household scale, where a separate static-asset container, a config-file layer, or a bundled certificate manager would each add a moving part that buys nothing.

## Considered Options

- **A third container serving the Client's static assets** (nginx/Caddy): rejected — Fastify serving `/assets/*` from the same image makes a Client/API version skew *impossible on a fresh load*, since the bundle and the API ship as one artifact. A separate asset container reintroduces exactly the skew the PWA already threatens.
- **A bundled reverse proxy owning TLS**: rejected — most self-hosters already run one (the reference deployment is an existing Caddy on another host), and certificate renewal is precisely the operational surface the PoC scope cut deferred. The repo ships a copy-pasteable Caddyfile block instead of a container.
- **A mounted config file** (YAML/JSON, env overrides): rejected — nothing in the instance's configuration is deeply structured. Real settings are per-User preferences and live in the database; what remains is a handful of secrets and URLs, which is what env vars are good at.
- **Blob storage on a filesystem volume** (message bodies, attachments in `/data/blobs`, metadata in Postgres): rejected for the PoC — 250k messages of body text is single-digit GB and Postgres compresses it, while a second store means a second backup, a second volume, and orphaned-blob reconciliation. The blob accessor is a seam so this can be revisited under real scale.
- **Auto-generating the credential key into a volume on first boot**: rejected — it silently turns a Docker volume into a secret store, so a `docker volume rm` destroys every Mail Account's credentials with no warning, and it makes the ordinary "just recreate the container" instinct dangerous. The key is an operator-supplied env var and the app refuses to boot without it.
- **Migrations as a separate one-shot service** the operator runs deliberately: rejected — a second manual step is the step that gets skipped during a mid-dogfood upgrade. Migrations run in the app's own boot path, fail closed, and are serialised by a Postgres advisory lock.
- **Semver releases from day one** (release-please/changesets), or **`:latest` only**: rejected both — semver machinery has no public consumer yet, and `:latest` alone makes "go back to the image that worked an hour ago" impossible.

## Consequences

- **`PUBLIC_URL` is required and fail-closed**, and is the single source of truth for the WebAuthn RP ID and origin, cookie scope, and Web Push. It is not derived from forwarded headers, because a misconfigured proxy would then silently register passkeys against the wrong RP ID. Changing `PUBLIC_URL` later invalidates every registered passkey: moving domains is a re-enrollment event, not a config edit.
- **`MAIL_CREDENTIAL_KEY` is operator-supplied** (`openssl rand -base64 32`, per ADR-0003) and the app refuses to boot without it. Losing it costs re-authentication of every Mail Account, not loss of mail — a bounded cost that justifies the explicit mechanism over a magical one. `key_version` remains the rotation path.
- **Migrations are forward-only**: there are no `down` migrations, and the app will not serve traffic if one fails. Rolling an image back across a migration boundary therefore points old code at a new schema, so the documented upgrade ritual is `pg_dump` → `pull` → `up -d`, and rollback is restore-the-dump *plus* re-pin. The immutable `:sha-<short>` tag is the rollback handle; the dump is what makes it usable.
- **The dump matters more than "mail is re-syncable" suggests.** Everything ADR-0006 made an App Feature — Gatekeeper verdicts, Pins, Labels, Drafts, Pending Sends — exists only in Postgres. IMAP gives the mail back; it does not give back the screening decisions accumulated over the dogfood.
- **`pgdata` + `.env` is the complete backup surface**; the `app` container holds no state and is disposable.
- **An old Client may call a new API for one upgrade cycle** (a service worker can serve a cached bundle offline). The wire contract stays additive-only per the thin-client research, so an out-of-date Client is missing features rather than broken; the API advertises a build id so the Client can prompt a reload, but that UX is the Client's design, not the deployment's.
- **The operator CLI ships inside the app image** (`docker compose exec app mail …`). With no System Mailer recovery flow at PoC, it *is* account recovery, and sharing the image means it reuses the real argon2id hasher and credential AEAD rather than hand-written SQL.
- **First-run Owner claiming is gated by a one-time token printed to the container logs**, so a publicly reachable fresh instance cannot be claimed by whoever finds it first.
- **The app binds `${MAIL_BIND:-127.0.0.1:3000}`** — loopback by default so the safe case needs no thought, one `.env` line when the reverse proxy lives on another host. Postgres publishes no port at all. With an off-host proxy, app traffic crosses the LAN as plaintext HTTP while `PUBLIC_URL` says `https://`; `trustProxy` is what keeps cookies and WebAuthn correct.
- **Postgres is pinned to a major version**, minors float. A major upgrade is a manual dump/restore: the official image refuses to start against a data directory from another major, which is the correct loud failure.
- Runtime is `node:22-bookworm-slim`, not alpine (musl and native argon2/crypto builds), non-root, with an init shim so `SIGTERM` reaches Node and IMAP IDLE connections close cleanly rather than being severed mid-write. The root `compose.yaml` never builds; the development stack, including a local IMAP test server, is a separate concern.
