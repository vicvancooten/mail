# Real-time delivery is SSE hints to open Clients and Web Push to closed ones

A change in the Sync Backend reaches a device over one of two channels, both carrying only a
**Sync Hint** and never mail state: an **SSE** stream (`GET /events`) to Clients that are open, and
**Web Push** to Clients that are not. Both are fanned out from Postgres `LISTEN/NOTIFY`, emitted in
the same transaction that writes the change. This upgrades the *signal* that
[ADR-0011](0011-one-delta-endpoint-with-per-collection-state-tokens.md) specified 30s visible-only
polling as a fallback for; the Client still pulls its deltas from `POST /sync`, so push-then-pull is
unchanged and polling drops to a slow safety net rather than disappearing.

## Considered options

- **WebSocket instead of SSE**: rejected. Everything upstream already has a home — mutations are
  `POST`s, deltas are `POST /sync` — so bidirectionality would go unused, while the upgrade handshake
  is the thing an arbitrary operator-supplied reverse proxy ([ADR-0009](0009-deployment-is-a-single-image-two-service-compose.md))
  breaks silently. SSE is plain HTTP with free reconnect-and-backoff.
- **Web Push as the only channel, polling untouched**: rejected — it makes a desktop tab you are
  actively looking at the slowest surface in the system, and ties every live update to a permission
  the User may have denied.
- **An in-process event bus instead of `LISTEN/NOTIFY`**: rejected even though the PoC is a single
  process. An emitter fires before commit or after it; before races a reader into seeing nothing,
  after needs its own bookkeeping. `NOTIFY` inside the writing transaction is correct by
  construction, costs ~30 lines, and makes ADR-0005's "the sync engine is a liftable module" real
  rather than aspirational.
- **Tickle-only pushes** (empty payload, service worker fetches before showing): rejected. Chrome
  requires `userVisibleOnly`, so a locked phone on a flaky connection would show "New mail" with no
  sender — worse than the client being replaced, and the notification *is* the mobile experience.
  Payloads are end-to-end encrypted to the subscription's keys, so the relaying push service sees
  ciphertext either way, which is most of the privacy argument for a tickle.
- **Notification action buttons enqueuing into the pending-mutation overlay**
  ([ADR-0010](0010-store-as-truth-with-a-pending-mutation-overlay.md)): rejected. The overlay exists
  to make the *UI* feel instant, and a service worker has no UI, no leader tab, and no way to render
  a rollback — it would be a second writer racing the leader for nothing.

## The two channels

**SSE.** The Web Locks leader tab that already owns Dexie writes owns **one** connection for the
whole User, all Mail Accounts, relaying to sibling tabs over `BroadcastChannel`. Per-tab connections
would eat five of the browser's six per-origin HTTP/1.1 sockets and starve `POST /sync`. Auth is the
existing httpOnly session cookie — never a token in the query string, which is what `EventSource`
tempts you into. A `:heartbeat` comment every ~25s proves liveness and defeats proxy idle timeouts; a
missed heartbeat drops the Client to its polling floor until reconnect, per ADR-0011's
degrade-don't-fail posture. There is no `Last-Event-ID` replay: state tokens already make a
reconnect-then-sync lossless, so replaying hints would buy nothing.

**Web Push.** Payloads carry sender display name, subject, and the stored Snippet. The VAPID keypair
comes from env (`MAIL_VAPID_PUBLIC_KEY` / `MAIL_VAPID_PRIVATE_KEY`), generated by the operator CLI
that already ships in the image — auto-generating into the database would silently invalidate every
subscription on a volume-restore mismatch. Subscriptions are stored against the **User**, never the
Session (a subscription that dies with a 60-day cookie rotation is one that stops working silently),
are pruned on the first `404`/`410` from the push service, and are **dropped wholesale when
`PUBLIC_URL` changes** — the service worker origin has moved, so it is a re-enrollment event exactly
as it is for passkeys.

## The Notifier

Policy lives in a **Notifier** module that subscribes to the same committed change stream as the SSE
fanout, not in the sync engine. Inline evaluation would grow Gatekeeper knowledge, per-account
toggle reads, and four-hour coalescing windows into a component whose job is IMAP.

Push-worthy events, and nothing else:

- **New mail from an Approved Sender landing in the Inbox** — the primary case.
- **The coalesced Gatekeeper hold digest** naming senders, then 4h of silence (`docs/poc-scope.md`).
- **A permanently failed send** ([ADR-0007](0007-undo-send-is-a-backend-held-pending-send.md) makes
  this a requirement on this design): you walked away believing it was sent, so silence is the
  failure mode.
- **A Mail Account entering `Needs Reauth`** — sync is dead, and ADR-0011's banner only helps someone
  who opens the app.

De-duplication is persisted on `(message_id, kind)`, and for the two failure kinds it keys on the
**state transition** rather than the occurrence: `Needs Reauth` notifies once on entry and not again
until reauth clears it, a failed send once per Composition. Fire-and-forget would re-push the first
half of a 40-message batch after a container restart, and duplicate mail notifications are the
fastest way to make someone disable push forever.

Two mechanisms keep floods out, and there is nothing finer:

- **Only messages arriving via IDLE/delta on an already-live folder are notification-eligible.** The
  backfill's 250k messages are ineligible *by construction*, not by a date heuristic, so a re-sync or
  a `reset: true` can never re-notify a history.
- **A per-Mail-Account burst cap**: past ~5 pushes in a short window, collapse into one "N new
  messages" using the Gatekeeper digest's own coalescing, so there is one coalescing concept rather
  than two.

No quiet hours, no VIP filter, no per-device mute: the per-Mail-Account toggle is the entire
preference surface, per `docs/poc-scope.md`.

## Consequences

- **ADR-0011's "the Client is silent when healthy" gains one narrow exception.** That rule bans
  narrating *the system's own success* — sync ran, action landed. New mail arriving is **external
  news**, the one thing worth interrupting for. So a device whose window is visible suppresses the OS
  notification and shows an **inline toast** instead (sender + subject, click-to-open, ~6s,
  stacking capped at 3 and then collapsing to "N new messages" via the same burst rule). Suppressed
  only when that thread is already the open one; shown regardless of which view is on screen.
- **Suppression is decided in the service worker, not the server**: on push, skip the OS notification
  if `clients.matchAll({type:'window'})` finds a visible one. Server-side "which device is awake"
  tracking would make push delivery depend on SSE bookkeeping that a dropped connection instantly
  makes wrong. Every subscribed device is pushed; you never know which one is in someone's hand.
- **Notifications are tagged with their thread id**, so any delta marking the thread `\Seen` lets the
  service worker close stale notifications on other devices via `getNotifications({tag})`.
- **Action buttons post directly to the API.** Archive on a mail notification; Approve and Block on a
  *single*-hold Gatekeeper notification. A coalesced digest carries **no** actions — it deep-links to
  the Screener, since the sender is ambiguous. The service worker `POST`s the intent with a ULID
  idempotency key, registers a Background Sync tag if offline (Chrome/Android-only, which is where
  the priority is), and re-shows the notification on a hard failure. Truth arrives with the next
  delta.
- **A click always lands where the next decision is**: a thread for mail, the Screener for a digest,
  the restored Draft in the composer for a failed send, that Mail Account's settings for `Needs
  Reauth`. It focuses and routes an existing window rather than opening a second one.
- **The app-icon badge is unread Inbox threads across all Mail Accounts**, set by the leader tab on
  every delta — but the count comes from a **backend-supplied counter on the sync response**, not a
  `COUNT` over the Local Cache, which would silently cap at that cache's ~500-thread floor
  ([ADR-0009](0009-client-local-cache-is-a-disposable-indexeddb-cache.md)).
- **SSE hints are coalesced at the emitter to at most one every ~500ms per User**, merging the
  changed-collection union, so a 40-message IDLE burst becomes one or two syncs returning everything
  at once. `NOTIFY` stays one-per-transaction because the Notifier needs each one to evaluate
  per-message policy. Deliberately **not** debounced Client-side: a hint means "pull now", and a
  second timer would make latency the sum of two debounces.
- **Sync liveness now has two tiers, and only the process-wide one touches readiness** — closing the
  "sync died while `/healthz` stayed green" gap ADR-0009 (deployment) handed over. Each Mail Account
  stamps `last_progress_at` on an IDLE keepalive or a completed poll. One stale account is an
  account-level condition: the loop self-restarts with backoff and the Client shows a per-account
  staleness banner — never a container restart, never a push, because restarting the process to fix
  one unreachable server takes down the working accounts and arms a restart loop. Readiness fails
  only when **every** account is stale or the `LISTEN/NOTIFY` connection is dead. Staleness (a
  connectivity verdict, in-app only) stays distinct from `Needs Reauth` (a credential verdict,
  pushed).
- **Notification permission is asked for exactly twice at most**: an explicit "enable on this device"
  control in settings, plus one inline offer after the first successful triage session, tracked by a
  `notificationOfferShown` **Device Preference** in `localStorage` (device-truth by definition, so it
  rides ADR-0011's never-synced category). Never on load — a denial is effectively permanent and
  un-recoverable in-app. A denied device is a **fully functional Client**: SSE, toasts, and badges all
  work without Notification permission; it simply does not ring. The settings control then shows a
  *blocked* state explaining that browser site settings are the only way back, because
  `requestPermission()` after a denial resolves instantly and silently and would otherwise look like
  our bug.
- **The Snippet is computed once at ingest**, not at notification time, so the list row and the
  notification show the same text with no drift.
